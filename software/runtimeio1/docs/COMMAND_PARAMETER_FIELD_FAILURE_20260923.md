# Offboard mode confirmation timeout: ROS command parameter types

Candidate: `low-speed-commandparams1-20260923` (protocol 13, handshake 8).
Supersedes `low-speed-outputpair1-20260923`; preserve the old archive for diagnosis.

## Confirmed cause and scope

The field log reports two `seven_finite_vehicle_command_parameters_required`
rejections before `LOW_SPEED_PROFILE Offboard mode confirmation timeout`.
`FlightCommandRequest.params` is `float64[7]`. ROS Humble generates a NumPy
array for this field. `tuple(request.params)` retains `numpy.float64` elements.
The transport's strict `finite()` helper accepts only built-in Python int/float,
so seven valid values are rejected before any COMMAND_LONG serial write.

This is a separate defect from the previous cross-publication setpoint pairing
failure. The old transport unit tests used built-in floats; the old ROS command
harness replaced the transport's `send_vehicle_command` with a recorder. Neither
test crossed this type boundary. The prior 235-test pass was therefore insufficient
to demonstrate a working physical command path.

The same rejection was reproduced locally for Offboard, ARM, DISARM, LAND and RTL
using generated/serialized ROS requests and the production transport. Five positive
regressions failed before the fix; 28 negative cases passed.

The Bridge now explicitly converts each parameter to Python float at the ROS
boundary. The transport still rejects non-finite values, forced ARM, unsupported
mode requests and nonzero LAND/RTL parameters. Ownership, approval, exact contract,
request lease, one-second TX warmup and current TX evidence checks remain intact.
No public API, ROS message, enum or PX4 configuration changes are required.

The later `setpoint_publication_pair_missing_or_stale` log is not evidence that
the preceding command reached PX4. This excerpt alone cannot determine whether
that subsequent missing pair was a termination transition or an independent
publication gap. The Home release line reports approval retirement and fresh
landed/disarmed observation; it does not prove a successful flight.

## Verification boundary

`test_vehicle_command_transport.py` passes commands generated by the production
Controller through ROS serialization, production Bridge guards and the production
MAVLink transport. It checks five valid commands, each of seven parameter positions
containing NaN/+Inf/-Inf, and forced ARM/mode/LAND/output-disabled/preflight/epoch/
lease rejections. A localhost DDS test uses the real request subscription with all
Bridge timers cancelled, so no USB open is possible.

Default tests use an in-memory encoder and serial port. With
`JOLGWA_TEST_PYMAVLINK=1`, the tests require actual pymavlink MAVLink 2 encoding and
decode command IDs, destination and all seven parameters from the produced bytes;
only the serial port remains in memory. This is not PX4 ACK or flight validation.
The COMMAND_LONG and DO_SET_MODE wire definitions are documented at
https://mavlink.io/en/messages/common#COMMAND_LONG and
https://mavlink.io/en/messages/common#MAV_CMD_DO_SET_MODE.
